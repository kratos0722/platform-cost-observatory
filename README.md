# Platform Cost Observatory

Turn AWS cloud spend from a monthly surprise into something teams watch
*weekly*. This is a small, deterministic analytics pipeline over **AWS Cost &
Usage Report (CUR)-style** billing exports. It takes a flat CSV of line items
and produces four governance signals that answer the questions a platform /
FinOps team actually asks:

| Signal | Question it answers |
| --- | --- |
| **Tagging hygiene** | Which resources are missing required allocation tags, and how much spend is therefore unattributable? |
| **Cost allocation** | What does each owner / team / service / day cost, with untagged spend made explicit? |
| **Forecasting** | Given month-to-date run rate, where will each owner land by month end? |
| **Anomaly detection** | Which (owner \| service) spend spikes deserve a page today, and *why*? |
| **Budget tracking** | Will any owner's *forecast* month-end spend breach its budget — early enough to act? |

The pipeline is intentionally **deterministic and dependency-light** (pandas +
numpy, no network, no randomness at runtime) so results are reproducible in
tests and CI.

> **Note on data:** every byte of sample data in this repo is **synthetic** and
> generated by a seeded script (`scripts/generate_sample.py`). Account IDs,
> owners and costs are invented. Nothing here is derived from real billing data.

---

## The cost-governance story: tag → allocate → forecast → detect

Cloud bills are only as legible as their tags. The pipeline follows the same
path a human would:

1. **Tag.** You cannot manage what you cannot attribute. The first pass scores
   *tagging hygiene*: the share of rows (and dollars) carrying every required
   allocation tag (`owner`, `team`, `environment`), per-tag coverage, and the
   worst offenders ranked by untagged spend. This is the backlog of "go add
   tags here" work, sorted by how much money is at stake.

2. **Allocate.** With tags scored, spend is rolled up per owner / team /
   service / day. Crucially, untagged spend is not dropped — it lands in an
   explicit **`unallocated`** bucket, the number a platform team drives toward
   zero.

3. **Forecast.** For the current month, each owner's month-to-date spend is
   extrapolated to a month-end projection from the daily run rate (a linear
   least-squares trend is also available). Every projection carries the
   arithmetic behind it, so it is explainable, not magic.

4. **Detect.** Finally, each entity's daily series is scanned for spikes
   against a rolling `mean + k·stddev` baseline (with a minimum relative-jump
   gate so smooth series don't page on noise). Each flag comes with a plain
   reason string an on-call engineer can act on without rerunning the math.

## Architecture

```
platform-cost-observatory/
├── src/costobs/
│   ├── ingest.py       # load + validate + type-normalize a CUR-style CSV
│   ├── tagging.py      # tagging-hygiene flags, coverage %, worst offenders
│   ├── allocation.py   # groupby rollups with an explicit "unallocated" bucket
│   ├── forecast.py     # month-end projection (run_rate | linear), explainable
│   ├── anomaly.py      # rolling mean ± k·stddev (and day-over-day) spike flags
│   ├── report.py       # assemble the four signals into one JSON + text report
│   └── cli.py          # `python -m costobs` / `costobs` entry point
├── scripts/
│   └── generate_sample.py   # seeded synthetic CUR generator (NDA-safe)
├── sample_data/
│   └── cur_sample.csv       # committed output of the generator
└── tests/                   # pytest: unit fixtures + sample integration
```

Each module is a pure function over a `pandas.DataFrame` — no hidden state, no
I/O except `ingest` (read) and `cli` (print). The canonical schema produced by
`ingest.load_cur` is:

```
usage_date   datetime64[ns]   (normalized to the day)
account_id   string
service      string
resource_id  string
owner        string  (blank/whitespace -> <NA>)
team         string  (blank/whitespace -> <NA>)
environment  string  (blank/whitespace -> <NA>)
unblended_cost  float64
usage_amount    float64
```

Treating blank tags as `<NA>` at the boundary means every downstream module can
rely on "missing" and "empty string" being the same thing.

## Quick start

```bash
# 1. create an isolated environment
python -m venv .venv
source .venv/Scripts/activate        # Windows (Git Bash); use .venv/bin/activate on macOS/Linux

# 2. install
pip install -r requirements-dev.txt
pip install -e .

# 3. (optional) regenerate the synthetic sample — deterministic, seeded
python scripts/generate_sample.py

# 4. run the pipeline
python -m costobs --input sample_data/cur_sample.csv
```

### CLI

```
costobs --input PATH [--json] [--as-of YYYY-MM-DD]
        [--forecast-method run_rate|linear]
        [--k 3.0] [--window 7] [--min-rel 0.25]
        [--anomaly-group owner[,service]]
        [--required-tags owner,team,environment] [--top 10]
```

* `--json` emits the full machine-readable report (ideal for piping into a
  dashboard or a Slack bot) instead of the human-readable summary.
* `--as-of` sets the "today" the forecast projects from (defaults to the latest
  `usage_date` in the file).
* `--k` / `--window` / `--min-rel` tune anomaly sensitivity.
* `--anomaly-group` scans per owner by default, or per `owner,service` for
  finer attribution.

Equivalent library use:

```python
from costobs import ingest, report

df = ingest.load_cur("sample_data/cur_sample.csv")
result = report.build_report(df)       # nested, JSON-serializable dict
print(report.render_text(result))
```

## Design notes

* **Tagging coverage is measured two ways.** Row coverage counts line items;
  cost coverage weights by dollars. They differ (70.6% vs 59.7% on the sample)
  because untagged resources are disproportionately expensive — which is the
  point.
* **Allocation never loses money.** Missing `owner` / `team` / `environment`
  values route to an explicit `unallocated` label rather than being dropped, so
  per-owner totals always reconcile to the grand total.
* **Forecasts are explainable.** The default `run_rate` method is just
  `MTD / days_elapsed × days_in_month`; every row ships the intermediate values
  and a sentence describing them. A `linear` least-squares option captures
  within-month ramps.
* **Anomaly detection resists false alarms.** A day must clear *both* a
  statistical gate (`cost > mean + k·std`, baseline = the prior `window` days,
  current day excluded) *and* a materiality gate (`--min-rel` above the mean).
  A perfectly flat history has `std = 0` and never fires. This is what lets the
  detector flag a real spike while ignoring ordinary daily wobble.

## Development

```bash
pip install -r requirements-dev.txt
pip install -e .
pytest
```

Tests cover each module with small inline fixtures (tag-coverage math,
allocation sums, run-rate projections, spike-vs-noise discrimination) plus an
integration pass over the committed sample that asserts the known spike is
caught. CI (GitHub Actions) runs the suite on Python 3.11 and 3.12.
